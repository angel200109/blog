# TypeScript 在前端项目中的优缺点

## 简介

TS 在前端圈已经算是标配了，但也不是所有项目都适合上 TS。团队规模、项目周期、维护预期都会影响这个决策。

## 优点

### 类型安全，提前发现错误

这是 TS 最核心的价值。类型检查只在开发/编译时起作用，不影响运行时性能，但能在开发阶段拦截大量低级错误：

```ts
function add(a: number, b: number): number {
  return a + b
}

add(1, '2') // ❌ 编译报错，不用等上线
```

比起靠 code review 和测试来发现类型错误，编译器直接报错显然更快更稳。

### 更好的 IDE 体验

有了类型信息，IDE 能给出精准的自动补全、参数提示、跳转定义。特别是用第三方库的时候，不用翻文档就能知道一个函数接受什么参数、返回什么。

### 可维护性

团队协作时，类型定义就是天然的"接口文档"。一个 interface 写清楚字段名和类型，新同事接手代码时一目了然，不用猜这个变量里面是什么。

## 缺点

### 编译成本

JS 写完就能跑，TS 多一步编译。小项目几乎感觉不到，大项目首次编译可能要等几秒到十几秒。好在增量编译和 Vite/esbuild 这类工具已经把这个问题缓解了不少。

### 代码量增加

写类型标注确实多打一些字。不过对于有返回值的项目来说，类型带来的安全感和维护成本的下降通常远超多写的那几行。

### 过度类型化

有些人会陷入"体操"——把类型写得比业务逻辑还复杂。TS 的本意是帮人写代码，不是让人跟编译器搏斗：

```ts
// 正常写法
type Status = 'pending' | 'success' | 'error'

// 过度设计（别这么搞）
type Status = StatusEnum extends infer S
  ? S extends 'pending' ? ...
```

类型能准确描述意图就够了，不需要炫技。

## 实战场景

- **新项目**：直接用 TS 起手，配置 `strict: true`
- **维护中的项目**：衡量一下团队接受度和迁移成本，可以逐步迁移
- **快速原型/小工具**：纯 JS 更快，没必要上 TS
- **多人协作的中大型项目**：TS 几乎是必选

## 总结

TS 的收益集中在长期维护和团队协作上。如果你的项目生命周期超过 3 个月且不止一个人在写，上 TS 基本不会后悔。
